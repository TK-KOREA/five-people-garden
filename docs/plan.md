# 다섯 사람 아이디어 정원 — 개발기획서·디자인 가이드

Oct 9, 2026 · @TK

이 문서는 1단계 개발을 시작할 때 기준으로 삼는 기획서입니다. 개발 전에 7장 끝의 "정할 사항" 여덟 가지를 확정하면 바로 0단계 시험에 들어갈 수 있습니다.

## 1. 개요

이 페이지는 "한 아이 곁에 의미 있는 다섯 사람"이라는 관찰을 실제 방안으로 키우기 위해, 성도들이 아이디어를 나누고, 저장하고, 서로의 생각을 보며 이어 써서 발전시키는 공개 공간입니다. 혼자 정리하는 메모장이 아니라, 한 사람의 생각에 다른 사람의 덧붙임, 질문, 해 본 경험이 쌓여 자라는 것이 핵심입니다.

**이름(가칭): 다섯 사람 아이디어 정원**

- 부제: 한 아이 곁에 다섯 사람
- 은유: 아이디어를 씨앗으로 심고, 물을 주고, 싹이 나고, 시도해서 열매를 봅니다. 고전 3:6(심는 이와 물 주는 이가 있어도 자라게 하시는 분은 하나님이시라는 요지, 회복역 본문 문구는 확인 필요)의 그림과 맞닿아 있어, 기능 이름과 상태 이름이 모두 이 은유에서 나옵니다.

**쓰는 사람**

| 사용자 | 하는 일 | 권한 |
| --- | --- | --- |
| TK (관리자) | 상태 변경, 신고된 글 숨김, 질문 관리, 코드 교체, 데이터 내보내기 | 편집 코드 + 관리 코드 |
| 함께 고민하는 성도들 | 생각 나누기, 이어 쓰기(덧붙임·질문·해 봤어요) | 편집 코드 |
| 공개 방문자 | 읽기, 물 주기(공감), 저장 | 없음 |

**성공의 모습**

- 생각이 떠오른 순간 한 줄로 나눌 수 있다.
- 들어오자마자 다른 사람들이 나눈 생각이 보이고, 한 번 눌러 이어 쓸 수 있다.
- 다섯 연결 중 생각이 적은 곳이 한눈에 보여, 다음에 무엇을 생각할지 페이지가 먼저 알려 준다.
- 한 생각이 덧붙임, 질문, 해 봤어요를 거쳐 어떻게 자랐는지 기록이 남는다.

## 2. 설계 원칙

모든 기능은 아래 다섯 원칙을 통과해야 들어갑니다. 기능이 많아질수록 페이지가 또 하나의 프로그램 관리 도구가 되기 쉽기 때문입니다.

1. **프로그램이 아니라 생명.** 생각마다 "이 방안이 그리스도를 누리는 어른의 생명을 아이에게 흘려보내는가"를 묻습니다. 1단계에서는 연결별 생각 꺼내기 문장(5-1)이 이 물음을 대신하고, 3단계에서 생명 점검으로 따로 묻습니다. 행사 체크리스트가 되지 않게 합니다.
2. **다섯 연결은 배정 명단이 아니라 렌즈.** 친구, 부모, 봉사, 다른 부모, 조부모는 생각을 분류하고 빈 곳을 보는 관점일 뿐, 특정 아이에게 특정 어른을 배정하는 기능은 만들지 않습니다.
3. **개인정보 0.** 공개 페이지이므로 아이와 성도의 이름, 연락처를 저장하지 않습니다. 쓰는 사람도 "초등 고학년 부모"처럼 별칭으로만 표시합니다. 입력 중 이름이나 전화번호처럼 보이는 글이 있으면 저장 전에 알려 줍니다.
4. **나누기는 가볍게, 다듬기는 함께.** 한 줄로 나누고, 설명·나이대·상황·구절은 나중에 채워도 됩니다. 생각을 다듬는 일은 다른 사람의 이어 쓰기로 이루어집니다.

**5. 비교하지 않음.** 인기순 정렬, 사람별 글 수, 순위는 만들지 않습니다. 물 준 수는 1 이상일 때만 보이고, 상태의 뜻은 화면에 공개해 누군가의 평가로 읽히지 않게 합니다.

**다섯 연결 (분류 기준, 자녀를 가운데 둔 그림)**

| 연결 | 설명 |
| --- | --- |
| 친구 | 또래와 한두 살 위 선배 형제자매 |
| 부모 | 아이 자신의 부모, 가정 안의 신앙 생활 |
| 봉사 | 어린이 집회와 중고등부를 섬기는 성도 |
| 다른 부모 | 우리 아이를 자기 집 식탁에 앉히는 다른 가정 |
| 조부모 | 할머니, 할아버지, 연로한 성도 |

여기에 연결을 특정하지 않는 "함께(전체)" 분류를 하나 더 둡니다. 연결 이름은 설정 시트에서 읽어 오므로 관리 화면에서 바꿀 수 있습니다.

## 3. 기능 기획

화면은 아래쪽 탭 세 개(나눔, 연결, 저장함)와 어디서나 여는 "생각 나누기" 입력 화면으로 구성합니다. 첫 화면은 다른 사람의 생각이 흐르는 나눔 피드이고, 카드를 누르면 함께 다듬는 상세 화면이 열립니다.

### 3-1. 핵심 흐름: 나누기 → 보기 → 이어 쓰기 → 저장

| 기능 | 설명 |
| --- | --- |
| 생각 나누기 | 한 줄 제목만 필수(연결은 "함께"가 미리 골라져 있음). 설명, 나이대, 상황, 근거 구절은 "더 적기"에 접어 둠. 별칭은 프리셋 칩에서 고르고 기기에 기억. 연결을 고르면 생각 꺼내기 문장이 뜸(5-1) |
| 나눔 피드 | 최근 활동 순(나누기 또는 이어 쓰기 시각)으로 표시. 맨 위에 오늘의 질문 한 장(questions 탭에서 돌려 보여 주고, 질문에서 나누면 question\_id가 붙음). 카드에 최근 이어 쓰기 한 줄을 미리 보여 줌 |
| 다섯 연결 띠 | 피드 맨 위에 다섯 연결을 작은 원으로 표시. 원 안 숫자는 생각 수, 누르면 그 연결만 거름. 1단계는 숫자와 거르기, 2단계에 가장 적은 연결 점선과 "채우러 가기" 안내. 숫자는 서버가 전체 글 기준으로 셈(5-1 자동 규칙) |
| 함께 다듬기 | 카드 상세에서 덧붙임, 질문, 해 봤어요 세 종류로 이어 씀. 종류별로 거르기 |
| 물 주기 | 생각과 이어 쓰기 모두에 공감 표시. 같은 기기에서 하루 한 번 |
| 저장함 | 북마크한 생각을 모아 봄. 로그인이 없으므로 기기(브라우저)에 저장 |
| 편집 코드 | 읽기, 물 주기, 저장은 누구나. 나누기와 이어 쓰기는 코드가 있는 사람만. 처음 나누거나 이어 쓸 때 한 번 입력하면 기기에 기억하고, 코드가 바뀌면 다시 물음 |

**나이대**: 유아, 초등 저학년, 초등 고학년, 중고등부로 올라가기, 중고등부, 세대 함께

**상황**: 식탁, 집회, 나들이·놀이, 기도, 생일·특별한 날, 가정 방문, 기타

### 3-2. 생각을 키우는 장치

1. **첫 생각을 이어 주세요 (1단계).** 아직 이어 쓰기가 없는 카드에 이 안내를 띄워, 혼자 남은 생각이 없게 합니다.
2. **개인정보 경고 (1단계).** 저장 전에 제목, 설명, 이어 쓰기, 별칭에서 전화번호 형식이나 이름 패턴을 찾아 "학년이나 역할로 바꿔 써 주세요"라고 알려 줍니다.
3. **살펴봐 주세요 (1단계).** 누구나 글을 신고할 수 있고, 관리 화면에 모여 관리자가 숨깁니다.
4. **가장 적은 연결 안내 (2단계).** 피드와 연결 탭에서 생각이 가장 적은 연결을 짚고, 누르면 그 연결이 미리 선택된 채 나누기 화면이 열립니다.
5. **해 봤어요가 쌓이면 열매로 (1단계 자동, 2단계 모아 보기).** 자동 변경은 상태를 올리기만 합니다(이어 쓰기 → 싹, 해 봤어요 → 시도). 해 봤어요가 둘 이상이면 열매가 됩니다. 쉼만 관리자가 정합니다. 시도 기록 화면을 따로 두지 않습니다.
6. **가지 치기 (2단계).** 상세 화면의 "가지 치기"로 이 생각에서 갈라진 새 생각을 나눕니다. 갈라진 가지는 상세 화면 안에 접힌 한 줄로 보여 주고, 누르면 펼쳐집니다.
7. **Claude에게 묻기 복사 (2단계).** 생각과 이어 쓴 내용 전체를 정리된 질문 글로 복사합니다.
8. **나눔지 인쇄 (2단계).** 고른 생각과 이어 쓴 내용을 A4 한 장으로 인쇄합니다.

나중으로 미룬 것: 함께 생각 보드(이번 주 질문 하나에 각자 메모를 붙이고 묶어 아이디어로 옮기기), 생명 점검, 관점 렌즈, 섞어 보기. 나눔과 이어 쓰기가 자리 잡은 뒤에 붙입니다.

| 화면 | 보이는 것 | 주요 동작 |

| 관리 (관리 코드로만 열림, 탭에 없음) | 경고를 무시한 글과 신고된 글, 숨긴 글, 정원 상태, 최근 변경 이력, 질문 목록 | 본문 고치기, 숨김·되돌리기, 개인정보 지우기, 이번 주 소식 만들기, 코드 교체, 상태 변경, 질문 관리 |

### 3-4. 처음 오는 사람, 다시 오는 사람 (1단계)

로그인과 알림이 없으므로, 처음 온 사람이 무엇인지 알고 다시 온 사람이 무엇이 달라졌는지 보게 하는 장치를 1단계에 넣습니다.

| 장치 | 하는 일 |
| --- | --- |
| 처음 안내 카드 | 처음 열 때 한 번만 피드 맨 위에 세 줄: 이 페이지가 무엇인지, 다섯 연결이 누구인지, 코드 없이도 읽고 물 주기(공감)와 저장을 할 수 있다는 것. 닫으면 상단 "?"로 다시 봄. "?"에는 상태(씨앗·싹·시도·열매·쉼)의 뜻도 둠 |
| 지난번 이후 새로 | 마지막 방문 시각을 기기에 저장해, 그 뒤 활동한 카드에 "새로"를 붙이고 피드 위에 "지난번 이후 새 생각 n · 이어 쓰기 n"을 보여 줌 |
| 내가 나눈 생각 | 기기에 있는 edit\_token의 id로 내 생각과 이어 쓰기를 모아 보여 주고, 새로 달린 이어 쓰기 수를 표시(GET mine). 별칭이 여러 사람과 같아도 내 글을 찾을 수 있음 |
| 처음 나눈 분 표시 | 생각을 처음 나눈 기기에서 단 이어 쓰기에 "처음 나눈 분"을 붙임. 판정은 서버가 device\_id로 하고 화면에는 표시만 보냄 |
| 한 사람 글 접기 | 같은 기기의 글이 피드에 연달아 3개를 넘으면 "청년 형제의 생각 3개 더"로 접음. 나누기를 마치면 "다른 생각에 이어 써 볼까요?"를 보여 줌 |
| 질문에서 방안으로 | 오늘의 질문 버튼은 "이 질문에서 떠오른 방안 나누기". 입력란 위에 질문을 보여 주고 안내 글은 "그래서 해 볼 수 있는 것은?" |
| 생각마다 주소와 공유 | 생각마다 주소(`#/idea/I-…`)를 두고, 상세 화면에 "카톡으로 보내기"(navigator.share, 안 되면 링크 복사)와 인쇄 스타일(@media print)을 둠. A4 나눔지는 2단계 |
| 입력 도움 | 입력란 아래에 "자판의 마이크를 눌러 말로 써도 돼요". 제목이 60자를 넘으면 자르지 않고 넘친 부분을 설명으로 옮김 |
| 이번 주 소식 | 관리 화면의 버튼이 새 생각과 해 봤어요 3\~5개를 제목과 링크로 묶은 카톡용 글을 만듦. TK가 주 1회 단톡방에 붙여 넣음. 같은 글을 매주 TK 메일로 보내는 트리거(MailApp)는 선택 |

### 3-5. 코드 받고 넣기 (1단계)

- **배포**: 편집 코드는 교회 단톡방 공지로 한 번 알립니다. 공지에 `주소/#c=코드` 링크를 함께 올려, 그 링크로 열면 코드가 기기에 저장되고 주소창에서는 지워집니다. # 뒤의 값은 서버와 깃헙 기록에 남지 않지만, 링크를 전달받은 사람에게는 코드가 함께 가므로 단톡방 안에서만 씁니다.
- **묻는 때**: 코드는 보내기를 누를 때 묻습니다. 쓴 글은 기기에 임시 저장해 두었다가, 코드를 넣으면 그대로 보냅니다.
- **쉬운 코드**: 한글 단어와 숫자(예: 다섯사람1009)로 만들고, 공백과 대소문자는 무시합니다.
- **틀렸을 때**: 잠금은 틀린 그 기기에만 겁니다(편집 코드 10분에 10회). 한 분이 여러 번 틀려도 다른 분은 막히지 않습니다. 전체 기준은 공격만 막도록 넉넉하게 둡니다(6장).
- **코드를 바꿀 때**: set\_code를 하면 단톡방에 붙여 넣을 공지 문구(새 #c= 링크 포함)를 만들어 줍니다. 옛 코드를 넣은 기기에는 "코드가 바뀌었을 수 있어요. 단톡방 최근 공지를 봐 주세요"를 보여 줍니다.
- **기본 연결**: 나누기 화면은 "함께"를 미리 골라 두어, 어느 연결인지 몰라도 제목 한 줄만으로 나눌 수 있습니다.

## 4. 시스템 구조

권장 구조는 화면 파일(HTML, JS, CSS)을 GitHub Pages에 두고, Apps Script는 데이터만 주고받는 API로 쓰는 방식입니다. Apps Script로 서버를 만들고 깃헙에 공개한다는 처음 조건은 그대로 지키면서, 첫 화면 속도와 휴대폰 사용감에서 아래 표의 이점을 얻습니다.

```
[방문자 휴대폰] --① 화면 받기--> [GitHub Pages: index.html · app.js · style.css, 비밀 값 없음]
       |
       └--② GET · POST--> [Apps Script 웹 앱: doGet 읽기(캐시) · doPost 쓰기(잠금, 횟수 제한) · 스크립트 속성에 코드]
                                   |
                                   └--읽기 · 쓰기--> [Google Sheets: ideas · replies · questions · config · log · guard]
```

방문자는 깃헙에서 화면을 받고, 그 화면이 Apps Script에 데이터를 요청합니다. 편집 코드는 Apps Script 안에만 있어 공개 저장소에 드러나지 않습니다.

**두 방식 비교**

| 항목 | A. Apps Script 화면을 iframe으로 임베드 | B. 깃헙 화면 + Apps Script API (권장) |
| --- | --- | --- |
| 첫 화면 속도 | Apps Script가 매번 화면을 만들어 느린 편 | 깃헙에서 바로 뜨고, 저장해 둔 데이터를 먼저 보여 줌 |
| 구글 안내 문구 | 다른 사람이 열면 "다른 사용자가 만든 앱" 안내가 위에 붙을 수 있음 | 붙지 않음 |
| 휴대폰 사용감 | iframe 높이가 고정되어 이중 스크롤이 생기기 쉬움 | 보통 웹페이지처럼 자연스러움 |
| 공유 미리보기 | 내용이 iframe 안에 있어 제목·이미지 지정이 제한적 | 제목, 설명, 미리보기 이미지 지정 가능 |
| 필요한 설정 | setXFrameOptionsMode(ALLOWALL) | POST를 text/plain으로 보내 CORS 사전 요청을 피함 |
| 코드 관리 | 화면과 서버가 Apps Script 한곳에 | 화면은 깃헙(버전 이력), 서버는 Apps Script |

A로 가시더라도 기능 기획은 그대로 적용됩니다. 두 방식의 차이는 0단계 시험(7장)에서 실제 휴대폰으로 확인하고 정하시면 됩니다.

**배포 방식**

- Apps Script는 웹 앱으로 배포하고, 실행 사용자는 "나", 액세스는 "모든 사용자"로 둡니다. "Google 계정이 있는 모든 사용자"를 고르면 로그인하지 않은 방문자의 요청이 실패하므로 고르지 않습니다.
- 배포 주소는 깃헙의 app.js 설정 한 줄에만 넣습니다.
- 코드를 고칠 때는 새 배포를 만들지 않고 기존 배포를 새 버전으로 수정해 주소를 유지합니다.
- 화면의 요청은 헤더 없이 보냅니다. GET은 `fetch(url + '?action=…')`, POST는 `fetch(url, {method: 'POST', body: JSON.stringify(x)})`이며 Content-Type을 지정하지 않아 text/plain으로 갑니다. 사용자 정의 헤더나 application/json을 넣으면 사전 요청(CORS) 때문에 실패하므로, 코드는 모두 본문에 넣습니다.
- 응답은 script.googleusercontent.com으로 넘어가는 리디렉션을 거치므로 fetch의 기본값(follow)을 그대로 씁니다.

저장함은 기기(브라우저)에만 두므로 시트 탭이 없습니다.

**questions (질문)**: id(Q-yyyyMMdd-영숫자 6자), text(100자), order(숫자), active(참/거짓), created\_at.

**config (설정)**: key, values. 연결, 나이대, 상황, 상태, 별칭 목록을 여기서 읽어 화면의 칩을 만듭니다. 이름을 바꾸려면 이 탭만 고치면 됩니다.

**log (변경 이력)**: at, action, target\_id, before, after, author, admin\_name. action은 API의 action 이름을 그대로 씁니다(create, update, remove, reply, report, status, hide, unhide, question, set\_code). 물 주기는 행이 너무 빨리 늘어나므로 log에 남기지 않고 guard에만 남깁니다. 관리자가 둘 이상이어도 admin\_name으로 누가 했는지 구분합니다. 상태가 바뀐 날짜는 이 탭에서 계산합니다.

**guard (남용 방지)**: at, device\_id, action, target\_id, date(KST 날짜). device\_id는 기기마다 처음 열 때 만들어 브라우저에 두는 임의 id입니다. 방문은 기기×KST 날짜당 한 행(visit)으로 남겨 정원 상태 지표에 쓰고, 물 주기와 살펴봐 주세요는 기기×대상×KST 날짜당 1회로 이 탭에서 판단합니다. 30일 지난 행은 매일 도는 시간 트리거로 정리하되, 한 줄씩 지우지 않고 남길 행만 골라 한 번에 다시 씁니다.

### 5-1. 프리셋 (처음부터 채워 두는 값)

시트를 처음 만들 때 아래 값을 모두 채워 두어, 배포 첫날부터 빈 화면 없이 쓸 수 있게 합니다. 같은 값을 코드에도 DEFAULTS 상수로 두어, config 탭이 비거나 잘못돼도 화면이 깨지지 않게 합니다.

**한 번에 세팅하는 함수**

- `setupSheets()`: 탭 여섯 개를 만들고, 머리글 행 고정·보호, 열 너비, 글과 시간 열의 일반 텍스트 서식(@)을 넣은 뒤 프리셋을 채웁니다. 드롭다운 검증은 status, kind처럼 값이 하나인 열에만 겁니다. 여러 값을 쉼표로 담는 age, seat, setting은 서버 검사로 대신합니다. 이미 있는 탭과 행은 건드리지 않아 여러 번 실행해도 안전합니다.
- `setupProperties()`: 스크립트 속성에 EDIT\_CODE(성도들이 휴대폰으로 입력하기 쉬운 8자 이상), ADMIN\_CODE(16자 이상 임의값), REV(0)를 넣고 두 코드를 실행 기록(로그)에 보여 줍니다. 로그는 스크립트 편집 권한이 있는 사람이 볼 수 있으므로, 운영 전에 관리 화면에서 두 코드를 반드시 바꿉니다(1단계 완료 기준). SHEET\_ID는 스크립트가 붙은 시트에서 자동으로 읽습니다.
- `setupTriggers()`: 주간 백업(시트 사본, 최근 8개 보관)과 매일 guard 정리 트리거를 만듭니다.
- `resetPresets()`(관리자 전용): config와 questions만 프리셋으로 되돌립니다. 아이디어와 이어 쓰기는 지우지 않습니다.

**자동 규칙**

- **상태는 올리기만 합니다.** 이어 쓰기가 처음 달리면 씨앗 → 싹, 해 봤어요가 처음 달리면 씨앗·싹 → 시도. 해 봤어요가 둘 이상이면 열매가 됩니다. 쉼만 관리자가 정하며, 화면에는 "지금은 쉬는 중, 언제든 다시 이어 쓸 수 있어요"로 보여 줍니다. 상태 변경은 이어 쓰기 저장과 같은 잠금 안에서 처리합니다.
- **정렬**: 피드는 last\_activity\_at 내림차순, 같으면 id 내림차순. 고치기(update)는 last\_activity\_at을 바꾸지 않습니다. 새 아이디어는 씨앗, 별칭은 기기에 마지막 값을 기억합니다.
- **연결 띠 숫자**: 서버가 숨김·삭제를 뺀 전체 글로 셉니다. "전체"는 모든 글 수이고, 연결을 여러 개 고른 글은 각 연결에 1씩 셉니다.
- **가장 적은 연결**: "함께"를 빼고 다섯 연결 중 숫자가 가장 적은 곳. 같으면 seats 순서의 뒤쪽을 고릅니다.
- **오늘의 질문**: active인 질문을 order 순으로 늘어놓고, KST 2026-01-01부터 지난 날 수를 질문 개수로 나눈 나머지 번째를 고릅니다. 서버가 계산해 bootstrap에 넣습니다.

**개인정보 감지 프리셋** (저장은 막지 않고 경고만)

- 검사 대상: 제목, 설명, 이어 쓰기, 별칭(실명을 쓰기 가장 쉬운 칸)
- 전화번호: `01[016789][-.\s]?\d{3,4}[-.\s]?\d{4}`
- 이메일: `[\w.+-]+@[\w-]+\.[\w.]+`
- 이름처럼 보이는 말: 두세 글자 한글 뒤에 "이가, 이는, 이를, 이랑, 네 집, 네 가정"이 붙은 경우. 단 어린이, 아이, 형제, 자매, 부모, 성도 같은 제외 단어는 잡지 않습니다.
- 저장은 막지 않고 경고만 합니다. 오탐이 있을 수 있으므로 "그대로 나누기"를 함께 둡니다. 걸린 단어를 강조하고 "우리 아이", "○학년 아이"로 한 번에 바꾸는 버튼을 둡니다. 경고를 무시하고 저장된 글은 flagged로 표시해 관리 화면 맨 위에 올리고, TK에게 메일(MailApp)로 바로 알립니다.

## 6. API 설계와 보안

읽기는 GET 하나로 한 번에 받아 오고, 쓰기는 POST 하나에 action으로 구분합니다. 공개 페이지에 쓰기가 열려 있으므로 보안은 "막는다"보다 "망가져도 되돌린다"에 무게를 둡니다.

**엔드포인트**

| 요청 | action | 보내는 값 | 하는 일 |
| --- | --- | --- | --- |
| GET | bootstrap | 없음 | config, today\_question, counts(연결 띠 숫자), 피드 첫 page\_size개, next\_cursor |
| GET | feed | cursor, seat(선택) | 다음 피드. cursor = \`last\_activity\_at |
| GET | idea | id | 생각 하나, 이어 쓰기 전체, 갈라진 가지. 숨김·삭제된 글은 빼고, 대상이 숨김·삭제면 NOT\_FOUND |
| POST | check\_code | edit\_code | 편집 코드 확인만 |
| POST | create | edit\_code, device\_id, request\_id, title, detail, seat, age, setting, verse, author, question\_id, parent\_id | 생각 나누기. 응답에 id와 edit\_token(이때 한 번만) |
| POST | reply | edit\_code, device\_id, request\_id, idea\_id, kind, text, author | 이어 쓰기. 응답에 id와 edit\_token |
| POST | update | id, edit\_token 또는 admin\_code, 고칠 칸 | title, detail, age, seat, setting, verse만 고침 |
| POST | remove | id, edit\_token 또는 admin\_code | 생각이나 이어 쓰기 지우기(deleted 표시) |
| POST | water | device\_id, target\_id | 생각(I-)이나 이어 쓰기(R-)에 물 주기 |
| POST | report | device\_id, target\_id | 살펴봐 주세요 |
| POST | admin\_list | admin\_code, admin\_name | 신고·숨김 글, 최근 log |
| POST | status, hide, unhide, question | admin\_code, admin\_name, 대상과 값 | 상태 변경, 숨김과 되돌리기, 질문 관리 |
| POST | set\_code | admin\_code, admin\_name, which(edit 또는 admin), new\_code | 코드 교체 |
| POST | export | admin\_code, admin\_name | CSV 내보내기. edit\_token\_hash, device\_id, request\_id 열은 뺌 |
| GET | mine | ids(기기에 있는 내 글 id, 쉼표 구분, 최대 50개) | 내가 나눈 생각과 이어 쓰기, 각각의 새 이어 쓰기 수 |
| POST | erase | admin\_code, admin\_name, target\_id | 개인정보 지우기. 본문과 log의 before 값을 \[삭제\]로 덮어씀 |
| POST | digest, stats | admin\_code, admin\_name | 이번 주 소식 글 만들기, 정원 상태 지표 |

관리 코드는 URL에 남지 않도록 관리 action과 내보내기를 모두 POST로 보냅니다. 내보내기 응답은 화면에서 파일로 만들어 내려받습니다.

POST 본문은 JSON 문자열 하나이고, 서버는 `JSON.parse(e.postData.contents)`로 읽습니다. 응답은 항상 `{ok, data, error, rev}`입니다. Apps Script 응답은 HTTP 상태 코드를 바꿀 수 없으므로 실패는 `error = {code, message}`로만 알립니다. 코드는 BAD\_EDIT\_CODE, BAD\_ADMIN\_CODE, LOCKED\_OUT, RATE\_LIMIT, INVALID, BUSY, NOT\_FOUND 일곱 가지이고, 화면은 코드마다 8-6의 문구를 보여 줍니다. 같은 request\_id가 이미 저장돼 있으면 새로 저장하지 않고 처음 결과를 ok로 돌려줍니다. rev는 쓰기마다 1씩 올리는 번호(스크립트 속성 REV)로, 화면이 가진 rev와 다르면 새로 불러옵니다.

**보안과 남용 방지**

- **코드 보관**: 편집·관리 코드는 스크립트 속성에만 둡니다. 깃헙 저장소와 URL에는 넣지 않고 POST 본문으로만 보냅니다. 화면에서는 편집 코드를 localStorage에, 관리 코드는 탭을 닫으면 사라지는 sessionStorage에만 둡니다.
- **코드 대입 막기**: 틀린 시도는 기기별로 세어 편집 코드 10분에 10회, 관리 코드 10분에 5회를 넘으면 그 기기만 10분간 LOCKED\_OUT을 돌려줍니다. 공격을 막는 전체 기준은 넉넉하게 둡니다(편집 코드 1시간 200회, 관리 코드 1시간 30회). 편집 코드는 비교할 때 공백과 대소문자를 무시합니다(3-5).
- **edit\_token**: create와 reply 때 서버가 `Utilities.getUuid()`로 만들어 응답으로 한 번만 돌려주고, 시트에는 SHA-256 해시만 저장합니다. 화면은 localStorage에 `{id: token}`으로 보관합니다.
- **동시 쓰기**: 모든 쓰기는 `LockService.getScriptLock().waitLock(10000)` 안에서 처리하고, 10초 안에 잠금을 얻지 못하면 BUSY를 돌려줍니다. REV 증가, request\_id 중복 검사, 행 추가, 상태 자동 변경을 모두 같은 잠금 안에서 합니다.
- **횟수 제한**: 기기별 1분 10회와 전체 1분 60회는 CacheService로, 물 주기·살펴봐 주세요의 하루 1회는 guard 탭으로 판단합니다. CacheService는 한 값을 최대 6시간까지만 보관하므로 하루 단위 제한에는 쓸 수 없습니다. device\_id는 브라우저 저장소를 지우면 바뀌므로 완벽한 차단이 아니라 실수와 장난을 줄이는 정도입니다.
- **입력 검사**: 서버에서 길이(config의 limit\_\*), 목록 값, id 형식(`^[IRQ]-\d{8}-[a-z0-9]{6}$`)을 다시 검사합니다. 화면 검사는 편의일 뿐입니다.
- **화면 출력**: 사용자가 쓴 글은 항상 textContent로 넣습니다. innerHTML로 넣지 않아 스크립트 삽입(XSS)을 막습니다.
- **수식 주입**: 0단계 시험(2026-10-09, `docs/stage0-results.md`)에서 일반 텍스트 서식(@)만으로는 =로 시작하는 값이 수식으로 실행되고, appendRow는 값을 해석해 서식까지 덮어쓰는 것을 확인했습니다. 그래서 행은 appendRow로 넣지 않고, 새 행 범위에 @ 서식을 건 뒤 setValues로 한 번에 쓰며, 글 열의 값은 모두 앞에 작은따옴표(')를 붙입니다. 시트는 이 따옴표를 떼고 저장하므로 읽으면 원래 값이 나옵니다(16개 시험 값 모두 통과). 숫자 열은 숫자 그대로 씁니다. CSV 내보내기에서는 = + - @ 탭 줄바꿈으로 시작하는 칸 앞에 작은따옴표를 붙입니다.
- **캐시**: bootstrap은 CacheService에 `bootstrap_v{REV}` 키로 60초 둡니다. 쓰기가 일어나면 REV가 바뀌어 다음 요청은 바로 새 값을 받습니다. 한 값은 100KB까지만 넣을 수 있으므로 넘으면 캐시하지 않습니다. 화면은 마지막 응답을 기기에 저장해 먼저 보여 준 뒤, 새 응답이 오면 합치지 않고 통째로 바꿉니다(숨긴 글이 기기에 남지 않게).
- **읽기 성능**: 한 요청에서 탭마다 getValues는 한 번만 부릅니다. request\_id 중복 검사는 최근 키를 CacheService에 두어 시트 전체를 다시 읽지 않습니다.
- **시간**: appsscript.json의 timeZone을 Asia/Seoul로 두고, 시간 값은 `Utilities.formatDate(d, 'Asia/Seoul', "yyyy-MM-dd'T'HH:mm:ssXXX")` 문자열로 저장합니다. "하루"는 KST 날짜 기준입니다.
- **되돌리기**: log 탭에 바뀌기 전 값을 남기므로 관리 화면에서 이전 값으로 되돌릴 수 있습니다.

### 6-1. 예외 상황과 운영

여러 사람이 로그인 없이 함께 쓰는 공개 페이지이므로, 아래 상황을 1단계부터 처리합니다.

| 상황 | 처리 |
| --- | --- |
| 같은 글을 두 번 보냄(두 번 누름, 느린 연결) | 보낸 직후 버튼을 잠그고, 글마다 request\_id를 붙이고(다시 보낼 때도 같은 값), 서버가 같은 request\_id는 한 번만 저장 |
| 보내는 중 연결이 끊김 | 쓴 내용을 기기에 임시 저장하고, 다시 열면 "보내지 못한 글이 있어요"로 이어서 보냄 |
| 내 글 고치기·지우기 | 로그인이 없으므로 쓴 기기에만 edit\_token을 저장. 다른 기기에서는 관리자에게 요청 |
| 지워진 생각에 달린 이어 쓰기 | 이어 쓰기가 있는 생각을 지우면 제목과 본문을 비운 "지워진 생각이에요" 카드로 피드와 상세에 남기고, 이어 쓰기는 그대로 보여 줌. 이어 쓰기가 없으면 피드에서 사라짐 |
| 부적절하거나 개인정보가 든 글 | 누구나 "살펴봐 주세요"를 누르고 관리자가 숨김. 숨김은 삭제가 아니라 log에 남음 |
| 편집 코드 유출 | 관리 화면에서 코드를 바꾸면 기존 코드는 바로 무효. 그사이 쓴 글은 log로 확인해 숨김 |
| 시트를 사람이 직접 고침 | 머리글 행과 id 열은 보호 범위로 잠그고, 목록 값은 드롭다운 검증 |
| Apps Script 사용 한도 | 동시 실행 수와 하루 실행 시간에 한도가 있음. 60초 캐시로 읽기를 줄이고, 정확한 한도는 개발 전 구글 공식 할당량 문서로 확인 |
| 글이 많아짐 | 피드는 20개씩 이어 불러오기. 수천 행까지는 시트 한 장으로 충분하다고 가정하고, 느려지면 오래된 "쉼" 글을 보관 탭으로 옮김 |
| 실제 아이 이름이 든 글 | 관리자가 본문만 고치거나(update) 숨김. 쓴 기기에는 "이름이 있어 잠시 가렸어요. 역할로 바꿔 다시 나눠 주세요"를 보여 줌. 관리 화면의 "개인정보 지우기"로 본문과 log의 before 값을 \[삭제\]로 덮어씀. 주간 백업에는 최대 8주 남음 |
| Apps Script 간헐 실패 | 0단계에서 요청의 약 7%가 8\~20초 뒤 구글의 404 페이지로 끝남. 화면 요청에 시간 제한(8초)과 한 번 다시 보내기를 두고, JSON이 아닌 응답은 연결 오류로 봄. POST는 request\_id로 중복 저장이 막혀 있어 다시 보내도 안전 |
| 카톡 안에서 연 경우 | 인쇄, 공유, 저장소 유지는 0단계에서 확인하고, 안 되는 기능에는 "브라우저로 열기" 안내를 보여 줌. 카톡과 다른 브라우저는 저장소가 따로라 코드와 내 글이 이어지지 않으므로, 안내 카드에 "단톡방 링크로 열면 계속 기억돼요"를 넣음 |
| 키보드가 입력줄을 가림 | visualViewport에 맞춰 입력줄을 올림. iOS 카톡에서의 동작은 0단계에서 확인 |

**운영**

- **관리자**: TK님(관리 코드 보유). 한 명을 더 두면 부재 중에도 숨김 처리가 가능하고, admin\_name으로 누가 했는지 구분합니다.
- **백업**: 매주 한 번 시트 사본을 자동으로 만들고 최근 8개만 보관합니다. 지운 개인정보도 백업에는 최대 8주 남습니다.
- **검색 노출**: 교회 안의 나눔이므로 기본은 검색엔진 비노출(noindex)입니다. 주소를 아는 사람만 찾아옵니다.
- **실행 계정**: 웹 앱은 "나로 실행"이므로 시트 권한과 사용량이 배포한 구글 계정에 묶입니다. 개인 계정보다 사역용 계정을 권장합니다.
- **저장함 한계**: 기기에만 저장되므로 휴대폰이나 브라우저를 바꾸면 사라집니다. 2단계에서 "저장함 내보내기"로 보완합니다.
- **첫 공지**: "아이 곁에 의미 있는 다섯 사람을 세우는 방법을 함께 나누는 곳이에요. 읽기와 공감은 누구나 할 수 있고, 생각을 나누려면 이 링크로 열어 주세요. \[#c= 링크\] 글을 지우고 싶으면 \[관리자 별칭\]에게 말씀해 주세요." 1주와 2주 뒤에 이번 주 소식으로 다시 알립니다.
- **정원 상태** (관리 화면, 관리자만): 쓴 기기 수, 이어 쓰기가 달린 생각 비율, 해 봤어요 수, 연결별 생각 수, 이틀 이상 다녀간 기기 수. 2주 뒤 목표 예시는 쓴 기기 8대 이상, 이어 쓰기 비율 50% 이상, 해 봤어요 2개 이상이며 교회 규모에 맞춰 조정합니다.

## 7. 단계별 개발 계획과 결정할 사항

0단계 연결 시험 뒤 세 단계로 나누어, 1단계가 끝나는 순간부터 실제로 아이디어를 모을 수 있게 합니다. 기간은 TK님의 작업 여유에 맞춰 정하시도록 비워 두었습니다.

1. **0단계: 연결과 기기 확인(하루).** 깃헙 시험 페이지에서 GET과 POST가 오가는지, 일반 텍스트 서식 열에서 =로 시작하는 값이 글자로 남는지, 첫 응답과 이후 응답 시간을 확인합니다. 카톡 인앱 브라우저(iOS, Android)에서 localStorage 유지, `#c=` 링크, 공유, 인쇄, 키보드와 입력줄, 시스템 글꼴을 가장 크게 했을 때의 화면도 확인합니다. 4장의 구조 선택이 이때 확정됩니다.
2. **1단계: 나누고 이어 쓰기.** 시트와 세팅 함수 네 개, bootstrap·feed·idea·mine·check\_code·create·reply·update·remove·water·report API, 코드 받고 넣기(3-5), 처음 오는 사람과 다시 오는 사람 장치(3-4), 나눔 피드와 다섯 연결 띠(숫자와 거르기), 오늘의 질문, 생각 나누기 화면, 함께 다듬기 상세, 내 글 고치기·지우기, 상태 자동 변경, 개인정보 경고와 flagged 메일 알림, 글자 크기 3단계, 관리 화면(admin\_list, 본문 고치기, hide, unhide, erase, digest, stats, set\_code), 주간 백업과 guard 정리 트리거. 여기까지면 바로 함께 쓸 수 있습니다.
3. **2단계: 연결과 저장.** 연결 탭 지도, 가장 적은 연결 안내, 나이대로 거르기(feed에 age), 저장함과 저장함 내보내기, 가지 치기, Claude에게 묻기 복사, A4 나눔지 인쇄, 관리 화면의 상태 변경·질문 관리·변경 이력 보기·되돌리기·CSV 내보내기, 이번 주 소식 메일 트리거(선택).
4. **3단계: 함께 생각 보드.** 이번 주 질문 보드와 메모 묶기, 생명 점검, 관점 렌즈, 섞어 보기.

**단계별 완료 기준**

- **0단계**: 시험 페이지에서 GET과 POST가 오가고, 서버 응답 시간과 캐시된 화면 표시 시간을 각각 기록한다. 목표는 캐시된 화면 1초 안, 서버 응답 3초 안이다. 오래 쉬었다가 처음 부를 때는 더 걸릴 수 있어 그 값도 따로 적는다. 카톡 인앱에서 안 되는 기능 목록을 적는다.
- **1단계**: 편집 코드가 있는 세 사람이 각자 휴대폰으로 생각을 나누고 서로 이어 쓴 뒤, 새로고침해도 그대로 보인다. 연로한 성도 한 분이 큰 글씨 설정으로 단톡방의 `#c=` 링크를 열어, 도움 없이 생각 하나를 나눈다. 코드가 없는 기기에서는 보낼 때 코드를 묻고, 쓴 글은 사라지지 않는다. 전화번호를 넣으면 경고가 뜨고, 같은 글을 두 번 눌러도 한 번만 저장된다. 실명이 든 시험 글을 고치고 지운 뒤 시트와 log에 이름이 남지 않는다. 관리 화면에서 두 코드를 바꾼 뒤 처음 코드는 무효다. 백업과 guard 정리 트리거가 실제로 한 번 돈다. 마지막으로 app-qa-test 스킬 점검을 통과한다.
- **2단계**: 가장 적은 연결 안내가 실제 숫자와 맞고, 저장함이 새로고침 뒤에도 남는다. 내보낸 CSV에 비공개 열이 없다.
- **3단계**: 보드 메모를 묶어 아이디어로 옮기면 원래 메모와의 연결이 남는다.

**TK님이 정할 사항**

- [ ] 페이지 이름: "다섯 사람 아이디어 정원"으로 갈지
- [ ] 구조: 권장안(깃헙 화면 + Apps Script API)으로 갈지, iframe 임베드로 갈지 (4장, 0단계 시험 뒤 확정)
- [ ] 관리자: TK님 외에 한 명 더 둘지 (편집 코드는 단톡방 공지로 배포하는 것으로 정함, 3-5)
- [ ] 프리셋 확인: 다섯 연결 설명, 나이대·상황 목록, 별칭 칩, 질문 네 개 (5-1)
- [ ] 첫 씨앗 다섯 개를 공지 전에 세 사람이 이어 쓰기까지 달아 두고 시작할지, 빈 채로 시작할지
- [ ] 검색 노출: 기본 비노출로 둘지

## 8. 디자인 가이드

콘셉트는 "이른 아침의 텃밭"입니다. 따뜻한 미색 바탕에 흙과 잎의 색을 쓰고, 장식보다 여백으로 차분함을 만듭니다. 휴대폰에서 한 손으로 쓰는 것을 기준으로 설계하고, 넓은 화면에서는 가운데 720px 폭으로 보여 줍니다.

### 8-2. 글꼴

- 본문과 화면: Pretendard (jsDelivr CDN, 가변 글꼴 하나로)
- 성경 구절: Noto Serif KR. 구절에만 써서 말씀이 화면 안에서 구별되어 보이게 합니다.
- 크기는 rem으로 지정합니다: 제목 1.5, 소제목 1.1875, 본문 1, 보조와 칩·배지 0.875rem(14px, 최소값). 줄 간격은 본문 1.6, 제목 1.3.
- 화면 위 "가" 버튼으로 글자 크기 3단계(100/125/150%)를 고르고 기기에 기억합니다. 큰 글씨에서는 연결 띠를 두 줄로 내리고, 원 안의 숫자는 원 아래로 옮깁니다. 휴대폰 시스템 글꼴 크기가 카톡 인앱에 반영되는지는 0단계에서 확인합니다.
- 굵기: 400(본문), 600(카드 제목, 버튼), 700(화면 제목)만 씁니다.

### 8-3. 간격과 모양

- 4px 단위. 주로 8, 12, 16, 24, 32를 씁니다. 화면 좌우 여백 16.
- 모서리: 칩 999(알약), 카드 16, 시트 위쪽 24.
- 그림자 대신 1px 테두리(--line)로 구분합니다. 떠 있는 버튼 하나에만 옅은 그림자를 씁니다.
- 누르는 영역은 최소 44 × 44px.

### 8-4. 구성 요소

| 요소 | 규칙 |

### 8-5. 움직임

- 카드가 새로 생기면 아래에서 8px 올라오며 나타남(200ms).
- 상태가 열매로 바뀌면 배지가 한 번 살짝 커졌다 돌아옴. 그 외 장식 움직임은 없음.
- 사용자가 움직임 줄이기를 켜 두었으면(prefers-reduced-motion) 모든 움직임을 끕니다.

### 8-7. 접근성

- 글자와 바탕의 명암비는 본문 4.5:1 이상입니다. 2026-10-09에 계산한 결과, 본문·보조 글자, 주색 버튼, 다섯 연결 배지, 상태 글자 색, 다크 모드 조합은 모두 4.69:1 이상으로 통과했습니다.
- 상태의 점·배지 색과 --sun(#D99A2B)은 흰 바탕에서 2.4\~2.8:1이라 글자에 쓰면 안 됩니다. 점과 배지 바탕에만 쓰고, 글자는 상태 색 표의 글자 색을 씁니다.
- 상태와 연결은 색만으로 구별하지 않고 아이콘, 글자, 숫자를 함께 씁니다.
- 연결 지도에는 같은 내용을 담은 목록을 화면 읽기 프로그램용으로 함께 둡니다.
- 키보드로 모든 버튼에 갈 수 있고, 아래 시트가 열리면 포커스가 시트 안에 머뭅니다.
